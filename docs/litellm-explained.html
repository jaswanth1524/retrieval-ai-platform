LiteLLM in DocRAG

Why it's there, exactly what it does, and a full worked example — for the ollama and openai providers as configured in this repo.

1. What LiteLLM actually is

LiteLLM is a thin translation library. Every LLM provider — OpenAI, Anthropic, Ollama, Azure, Bedrock, 100+ others — has a slightly different HTTP API. LiteLLM gives one function, litellm.completion(model=..., messages=..., ...), that accepts an OpenAI-style messages list and internally routes to whichever provider the model string names, then normalizes the response back into the same OpenAI-style shape (response.choices[0].message.content) no matter which provider actually answered.

Why that matters here: DocRAG's generation code (api/generation.py) is written once, against that one shape. Swapping the backing model — local Ollama vs. hosted OpenAI — is a configuration change, not a code change or a second code path.

2. Why DocRAG uses it (the project rule)

Per CLAUDE.md's provider rules:

  • Generation provider and embedding provider are separate config knobs — changing one never touches the other.
  • Default generation is local Ollama — self-hostable, no API key required, no data leaves the machine.
  • OpenAI generation is optional, user-selectable, never required for upload/indexing.
  • Embeddings (bge-small-en-v1.5) always run locally via FastEmbed, regardless of which generation provider is picked. LiteLLM is only in the generation path — it never touches embeddings, retrieval, or reranking.

LiteLLM is the mechanism that makes "swap generation provider without touching retrieval" actually true in code, not just in a settings file.

3. Where it sits in the pipeline

A question only reaches LiteLLM after retrieval and reranking are done — it never sees raw documents, only the already-selected context:

1. Retrieve — dense (bge-small) + sparse (BM25) search in Qdrant, fused with Reciprocal Rank Fusion (k=60). api/retrieval.py
↓
2. Rerank — cross-encoder (bge-reranker-*) scores the fused top-N, keeps top-K. api/reranking.py
↓
3. Build prompt — top-K chunks formatted into a grounded system+user message pair with citation markers. api/generation.py: build_grounded_messages
↓
4. LiteLLM call — completion_model_and_kwargs() picks the model string + provider kwargs; litellm.completion(...) makes the actual request. api/generation.py: LiteLLMGenerator.complete
↓
5. Extract + cite — pull text out of the response, keep only sources the answer actually cited. extract_completion_text, cited_sources

4. The provider switch, exactly

This is the whole trick — one function decides the LiteLLM model string and extra kwargs from settings:

def completion_model_and_kwargs(settings: AppSettings) -> tuple[str, dict[str, str]]:
    provider = settings.llm_provider.lower().strip()
    if provider == "ollama":
        return f"ollama/{settings.llm_model}", {"base_url": settings.ollama_base_url}
    if provider == "openai":
        if not settings.openai_api_key:
            raise GenerationConfigError("OPENAI_API_KEY is required when LLM_PROVIDER=openai.")
        return settings.openai_model, {"api_key": settings.openai_api_key}
    raise GenerationConfigError(f"Unsupported LLM_PROVIDER '{settings.llm_provider}'.")
ProviderModel string sent to LiteLLMExtra kwargWhat LiteLLM does with it
ollamaollama/qwen2.5:latestbase_url=http://host.docker.internal:11434Sends an HTTP request to your local Ollama server's /api/chat-equivalent endpoint. No API key, no internet.
openaigpt-5-miniapi_key=sk-proj-...Sends a real HTTPS request to OpenAI's API using the standard OpenAI SDK under the hood.

The ollama/ prefix is a LiteLLM convention — it's how LiteLLM's internal router knows "don't call OpenAI's API with this string, call the Ollama provider adapter instead." Without the prefix, LiteLLM would try to look up qwen2.5:latest as an OpenAI model and fail.

Per-request override, not global mutation

The frontend's provider dropdown doesn't change server config — it passes llm_provider on the /questions request. RagPipeline.answer handles it like this:

generation_settings = (
    self._settings.model_copy(update={"llm_provider": llm_provider})
    if llm_provider is not None
    else self._settings
)
return generate_grounded_answer(..., settings=generation_settings)

model_copy makes a new settings object for that one call — the shared, cached settings singleton is never mutated. Two concurrent users, one asking via Ollama and one via OpenAI, don't interfere with each other. Retrieval and reranking always use the base settings — embeddings stay local no matter what generation provider was requested, per the CLAUDE.md rule.

5. Full worked example, start to end

Say you've uploaded a document containing this sentence, and Qdrant has already indexed it as chunk c_004a, page 2, section "Refunds":

"Refund requests must be submitted within 30 days of purchase. After 30 days, no refunds are issued."

You ask: "What is the refund window?" with the provider dropdown set to Ollama.

Step 1 — Retrieval + rerank produce one strong candidate

Dense + sparse search both surface chunk c_004a; RRF fusion ranks it #1; the cross-encoder reranker confirms it's the best match. This becomes the only context chunk passed forward (in practice there'd usually be a few).

Step 2 — build_grounded_messages constructs the prompt

[
  {
    "role": "system",
    "content": "You are DocRAG, a document question-answering assistant. Answer only from
the provided context. Do not use outside knowledge. If the context is insufficient,
explicitly say that the provided documents do not contain enough information. Cite
supporting sources with bracketed source numbers like [1]."
  },
  {
    "role": "user",
    "content": "Question:\nWhat is the refund window?\n\nContext:\n[1] filename=policy.txt;
page=2; section=Refunds; chunk_id=c_004a\nRefund requests must be submitted within 30 days
of purchase. After 30 days, no refunds are issued.\n\nInstructions:\n- Use only the context
above.\n- Include citations using source numbers such as [1] or [2].\n- If the context is
insufficient, say so directly."
  }
]

Step 3 — the LiteLLM call actually made

With your current .env (LLM_PROVIDER=ollama, LLM_MODEL=qwen2.5:latest):

litellm.completion(
    model="ollama/qwen2.5:latest",
    messages=[...the two messages above...],
    temperature=0,
    max_tokens=512,
    timeout=60.0,
    num_retries=0,
    base_url="http://host.docker.internal:11434",
)

LiteLLM sees the ollama/ prefix, routes to its Ollama adapter, and issues the request to your local Ollama server instead of any hosted API. If you'd had the dropdown on OpenAI instead, the exact same call site would instead run:

litellm.completion(
    model="gpt-5-mini",
    messages=[...same two messages...],
    temperature=0,
    max_tokens=512,
    timeout=60.0,
    num_retries=0,
    api_key="sk-proj-...",
)

build_grounded_messages, the retrieval, and the reranking are completely unchanged between these two cases. Only completion_model_and_kwargs's output differs.

Step 4 — response comes back, gets normalized

Ollama's native response and OpenAI's native response have different raw shapes. LiteLLM converts both into the same object shape before extract_completion_text ever sees it:

response.choices[0].message.content
  == "Refund requests must be submitted within 30 days of purchase [1]."

Step 5 — citation filtering

cited_sources regex-scans the answer for [1], [2], etc., and keeps only the sources actually referenced (falling back to all sources if the model cited none). Here it kept source 1. The API returns:

{
  "answer": "Refund requests must be submitted within 30 days of purchase [1].",
  "sources": [
    {
      "source_number": 1,
      "filename": "policy.txt",
      "page": 2,
      "section": "Refunds",
      "chunk_id": "c_004a",
      "text": "Refund requests must be submitted within 30 days of purchase. After 30 days, no refunds are issued."
    }
  ]
}

6. Failure handling

Every LiteLLM call is wrapped:

try:
    response = self.completion_client(...)
except Exception as exc:
    raise GenerationError(f"Generation provider request failed: {exc}") from exc

LiteLLM/provider SDKs raise many distinct exception types (auth failure, connection refused, rate limit, model-not-found...) — rather than enumerate all of them, this boundary catches broadly and re-raises as DocRAG's own GenerationError, which api/main.py maps to a clean HTTP 502 instead of an opaque 500.

SettingPurpose
LLM_REQUEST_TIMEOUT_SECONDSPer-request timeout passed straight to LiteLLM (currently 60s).
LLM_NUM_RETRIESLiteLLM's built-in retry count. Set to 0 so a bad key or dead provider fails in ~seconds instead of retrying for ~40s before surfacing an error.
